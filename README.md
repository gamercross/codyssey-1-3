# Mini NPU Simulator (codyssey-1-3)

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 **십자가(Cross)** 와 **X** 중 어느 필터와 더 닮았는지 판정하는 Python 콘솔 프로그램입니다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `re`, `os`, `sys`)만 사용합니다.

> **점수 차이 의미 해석 예시**: Cross와 X 필터 간 MAC 점수 차이가 2.0 이상이면 최소 2개 이상의 픽셀에서 형태적 일치도가 뚜렷하게 갈림을 의미하며, 점수 차이가 EPSILON(1e-9) 미만이면 대칭 구조 또는 노이즈 상쇄로 인한 동점(판정 불가)을 나타냅니다.

## 실행 방법

```bash
python main.py                     # main.py 와 같은 폴더의 data.json 사용
python main.py path/to/data.json   # 다른 위치의 data.json 사용 (모드 2)
```

- Python 3.8 이상
- 실행 후 모드 번호를 입력합니다.
  - `1` 사용자 입력 (3×3): 필터 A, B → 저장 확인 → 패턴 입력 → MAC 결과/판정 → 3×3 성능 분석
  - `2` data.json 분석: 필터 로드 → 패턴 로드/검증 → 케이스별 PASS/FAIL → 성능 분석(3/5/13/25) → 결과 요약
  - `3` 보너스: N×N 패턴 생성기 + 2차원/1차원 MAC 성능 비교
- 모드 1 입력 예시 (한 줄에 숫자 3개, 공백 구분):

  ```
  0 1 0
  1 1 1
  0 1 0
  ```

> 저장소의 `data.json` 은 과제 스키마(`filters.size_N.{cross,x}`, `patterns.size_N_idx.{input,expected}`)에 맞춰 만든 예시입니다.
> 과제에서 받은 공식 `data.json` 이 있으면 같은 자리에 덮어쓰거나 경로를 인자로 넘기면 됩니다.

## data.json 스키마

```json
{
  "filters": {
    "size_5":  { "cross": [[...5x5...]], "x": [[...5x5...]] },
    "size_13": { "cross": [[...]],       "x": [[...]] },
    "size_25": { "cross": [[...]],       "x": [[...]] }
  },
  "patterns": {
    "size_5_1": { "input": [[...5x5...]], "expected": "x" },
    "size_5_2": { "input": [[...5x5...]], "expected": "+" }
  }
}
```

## 구현 요약

| 항목 | 방식 |
|---|---|
| 데이터 구조 | `Matrix` 클래스: n×n 2차원 리스트, `get(r, c)` / `set(r, c, v)` 로 위치별 읽기·쓰기. `from_rows()` 가 행 수·열 수·숫자 여부·기대 크기를 검증 |
| 라벨 정규화 | `normalize_label()`: 앞뒤 공백 제거 + 소문자화 후 표 조회. expected `'+'`→`Cross`, `'x'`→`X` / filter 키 `'cross'`→`Cross`, `'x'`→`X`. 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준 |
| 필터 선택 | 패턴 키 `size_{N}_{idx}` 에서 정규식으로 N 을 뽑아 `size_N` 필터 묶음을 고름. 비정형 키 처리 우선순위: 정규식 `^size_(\d+)_(\d+)$` 일치 시 해당 크기 필터 자동 매칭 → 정규식 불일치 비표준 키는 프로그램 중단 없이 해당 케이스를 즉시 FAIL 기록 후 정렬 순서에 따라 다음 패턴을 우선 검사 |
| MAC 연산 | `mac()`: 이중 `for` 문으로 같은 위치끼리 곱해 `total` 에 누적. N² 번의 곱셈·덧셈. 결과는 float. 디버깅 팁: `mac(pattern, flt, verbose=True)` 옵션을 주면 셀별 곱셈과 누적 total을 실시간 모니터링 가능 |
| 동점 정책 | `abs(a - b) < 1e-9` 이면 동점 → `UNDECIDED` (모드 1 에서는 "판정 불가"). 동점은 expected 와 같을 수 없으므로 모드 2 FAIL 처리. EPSILON(기본값 1e-9)은 부동소수점 오차 허용값이며, 변경 시 `main.py` 상단의 `EPSILON = 1e-9` 상수를 원하는 임계값(예: 1e-6)으로 수정하여 판정 감도를 조정할 수 있습니다. |
| 오류 처리 | 모드 1: 열 개수·숫자 파싱 오류 시 안내 및 예시 입력 출력 후 그 행렬을 처음부터 재입력. 모드 2: 키 형식·필터 없음·input 없음·크기 불일치·숫자 아님·라벨 정규화 실패를 **케이스 단위 FAIL** 로 남기고 계속 진행. 파일 없음/JSON 깨짐도 메시지만 출력 |
| 시간 측정 | `measure_stats()` / `measure_ms()`: 워밍업 1회 후 `time.perf_counter()` 로 **연산 함수 호출 구간만** 10회 재서 평균, 표준편차, 최소/최대(ms) 산출. 입력·출력·파일 읽기는 제외 |
| 보너스 | `make_cross(n)` / `make_x(n)` 패턴 생성기(성능 분석에서도 재사용), `Matrix.flatten()` + `mac_flat()` 1차원 버전과 비교 |

### LABEL_ALIASES 지원 별칭 목록
| 원본 키 / expected 값 | 정규화 결과 | 매핑 대상 |
|---|---|---|
| `'+'`, `'cross'`, `'Cross'`, `'CROSS'` | `Cross` | 십자가 필터 및 정답 라벨 |
| `'x'`, `'X'` | `X` | X자 필터 및 정답 라벨 |

- **동점 콘솔 출력 예시**:
  - 모드 1 (대화형): `판정: 판정 불가 (|A-B| < 1e-9)`
  - 모드 2 (일괄 분석): `판정: UNDECIDED | expected: 'Cross' | FAIL (동점(|Cross-X| < 1e-9) → UNDECIDED 처리 규칙에 따라 FAIL)`

## 결과 리포트

> **결과 리포트 요약 통계**: 총 9개 테스트 케이스 중 9개 통과(통과율 100%), 실패 0건으로 data.json에 정의된 모든 크기(5×5, 13×13, 25×25)의 패턴 및 라벨 규격 적합 판정 완료.

### 1. data.json 분석 결과

```
총 테스트: 9개
통과: 9개
실패: 0개
```

| 케이스 | 입력 | Cross 점수 | X 점수 | 판정 | expected(원본→정규화) | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | X | 1.0 | 9.0 | X | `x` → X | PASS |
| size_5_2 | 십자가 | 9.0 | 1.0 | Cross | `+` → Cross | PASS |
| size_5_3 | 십자가 + 잡음 2칸 | 9.0 | 3.0 | Cross | `+` → Cross | PASS |
| size_13_1~3 | 위와 같은 구성 | 1 / 25 / 25 | 25 / 1 / 3 | X / Cross / Cross | | PASS |
| size_25_1~3 | 위와 같은 구성 | 1 / 49 / 49 | 49 / 1 / 3 | X / Cross / Cross | | PASS |

N×N 십자가는 1 이 2N−1 칸, X 도 2N−1 칸이고 두 모양은 가운데 한 칸만 겹칩니다.
그래서 맞는 필터 점수는 2N−1, 틀린 필터 점수는 1 이 되어 두 점수 차이가 크게 벌어집니다.

### 2. 왜 실패가 0 이 되었는가

1. **라벨/스키마 문제를 정규화로 없앴다.** data.json 은 expected 에 `'+'`, `'x'` 를, 필터 키에 `'cross'`, `'x'` 를 씁니다. 이 문자열을 그대로 비교하면 판정 결과 `'Cross'` 와 expected `'+'` 가 서로 달라 **로직이 맞아도 전부 FAIL** 이 됩니다. 프로그램 안에서는 표준 라벨 `Cross` / `X` 두 개만 쓰고, 읽어 들이는 순간 정규화하므로 표기 차이가 판정에 섞이지 않습니다. 대소문자·앞뒤 공백도 함께 흡수합니다.
   - **normalize_label 분리 장점 사례**: 라벨 정규화 함수를 독립 분리함으로써 단위 테스트(Unit Test)를 개별 수행할 수 있고, 추후 Triangle 등 신규 라벨이 추가되더라도 판정 코드를 수정하지 않고 사전 매핑만 갱신(OCP 준수)할 수 있습니다.
   - **새 라벨 추가 절차**: 1) `main.py` 정책 상수에 `LABEL_TRIANGLE = "Triangle"` 정의 → 2) `LABEL_ALIASES` 딕셔너리에 `'triangle'`, `'^'` 등 별칭 매핑 추가 → 3) `make_triangle()` 패턴 생성기 및 필터 등록 순으로 안전하게 확장할 수 있습니다.
2. **크기를 키에서 읽어 맞는 필터를 골랐다.** `size_13_2` 의 13 을 뽑아 `size_13` 필터와 곱합니다. 크기가 다르면 MAC 을 시도하지 않고 `크기 불일치` 로 FAIL 처리하므로 IndexError 로 프로그램이 멈추지 않습니다.
3. **부동소수점 비교에 epsilon 을 썼다.** 이번 데이터는 정수라 오차가 생기지 않았지만, 실수 데이터에서는 `0.1 + 0.2 = 0.30000000000000004` 처럼 수학적으로 같은 값이 다르게 나옵니다. `==` 로 비교하면 진짜 동점을 한쪽 승리로 잘못 판정하고, `>` 만 쓰면 아주 작은 오차가 판정을 뒤집습니다. `|a − b| < 1e-9` 로 "사실상 같음"을 먼저 걸러 `UNDECIDED` 로 처리합니다.
   - **EPSILON(1e-9) 선택 근거 및 조정 팁**: IEEE 754 배정밀도(64비트 float)의 머신 엡실론(약 2.22e-16)에 대해 수천 번의 곱셈·누적 연산에서 누적될 수 있는 수치 오차를 흡수하면서도 유의미한 소수점 입력 차이(0.1 단위 등)는 온전히 보존하도록 1e-9를 선택하였으며, 입력 정밀도에 따라 `main.py` 상단에서 1e-6 ~ 1e-12 범위로 조정할 수 있습니다.
   - 모드 1 에서 필터 A `0.1 0.2 0 / 0 0 0 / 0 0 0`, 필터 B `0.3 0 0 / …`, 패턴 `1 1 0 / 0 0 0 / 0 0 0` 을 넣으면 A 점수 `0.30000000000000004`, B 점수 `0.3` 이 나오고, 판정은 `판정: 판정 불가 (|A-B| < 1e-9)` 입니다.

### 3. 실패 원인 진단 (의도적 오류 데이터로 확인)

일부러 망가뜨린 data.json 으로 돌려 보면, 프로그램이 멈추지 않고 케이스별 원인을 남깁니다. 원인은 세 갈래로 나눠 봅니다.

| 분류 | 예시 케이스 | 콘솔 메시지 |
|---|---|---|
| 데이터/스키마 | 키가 `size_N_idx` 가 아님 | `키 형식 오류 (size_N_idx 형태가 아님)` |
| 데이터/스키마 | `input` 없음 | `input 항목 없음 (스키마 오류)` |
| 데이터/스키마 | 셀에 `"a"` | `input 형식 오류: (5,3) 값이 숫자가 아닙니다: 'a'` |
| 데이터/스키마 | expected `"circle"` | `expected 라벨 정규화 실패: 'circle'` |
| 데이터/스키마 | `size_9` 필터 없음 | `size_9 필터 없음` |
| 데이터/스키마 | 5×5 키에 13×13 입력 | `크기 불일치: 필터 5×5, 패턴 13×13` |
| 수치 비교 | Cross 1.0 = X 1.0 | `동점(|Cross-X| < 1e-9) → UNDECIDED 처리 규칙에 따라 FAIL` |
| 로직 | 판정이 expected 와 다름 | `판정 X ≠ expected Cross` |

- 데이터/스키마 문제는 MAC 이전 단계(키 파싱 · 필터 선택 · `Matrix.from_rows` 검증)에서 걸러집니다.
- 수치 비교 문제는 MAC 은 끝났지만 점수 차이가 epsilon 안에 드는 경우입니다.
  - **UNDECIDED(동점) 발생 시 후속 조치 방안**: 점수 차이가 EPSILON 미만인 경우, 1) 센서/카메라 입력을 다시 획득하는 재측정(Retry)을 수행하거나, 2) EPSILON 임계값을 완화하거나, 3) 가중치가 부여된 2차 보조 필터(Secondary Filter)를 통한 재판정 파이프라인을 연계할 수 있습니다.
- 마지막 줄(판정 ≠ expected)만 남는다면 그때 비로소 MAC/판정 로직이나 필터 자체를 의심하면 됩니다.

### 4. 성능 분석과 시간 복잡도

모드 2 성능 분석 결과 (Apple Silicon, 크기별 10회 평균 및 변동성 지표):

| 크기 | 평균 시간(ms) | 표준편차(ms) | 최소/최대(ms) | 연산 횟수(N²) | 1회 곱셈·덧셈당 시간 |
|---|---|---|---|---|---|
| 3×3 | 0.0008 | 0.0001 | 0.0007 / 0.0011 | 9 | 약 88 ns |
| 5×5 | 0.0013 | 0.0000 | 0.0013 / 0.0015 | 25 | 약 52 ns |
| 13×13 | 0.0076 | 0.0022 | 0.0065 / 0.0139 | 169 | 약 45 ns |
| 25×25 | 0.0273 | 0.0078 | 0.0221 / 0.0459 | 625 | 약 43 ns |
| 101×101 (모드 3) | 0.2509 | 0.0152 | 0.2410 / 0.2820 | 10,201 | 약 25 ns |

- **시간 복잡도**: MAC 은 N×N 의 모든 칸을 한 번씩 곱하고 더하므로 연산 횟수는 정확히 N² 입니다. 따라서 한 변 크기 N에 대해 시간 복잡도는 **$O(N^2)$** 이며, 전체 입력 원소 수를 $M = N^2$ 이라 할 때 총 입력 크기에 대해 **$O(M)$** 선형 시간이 소요됩니다.
- 측정값도 이를 따릅니다. 5×5 → 25×25 는 N 이 5배, N² 가 25배이고, 시간은 0.0013 → 0.0273 ms 로 약 21배 증가합니다.
- 작은 크기에서 배율이 N² 보다 덜 늘어나는 까닭은 함수 호출 · 변수 준비 같은 **고정 비용**이 있기 때문입니다. N 이 커질수록 칸당 시간이 약 25 ns 로 수렴하며, 칸당 시간이 일정해진다는 것이 곧 시간이 N² 에 비례한다는 근거입니다.
- **장치별 노이즈 영향 및 재현성 체크 팁**: OS 백그라운드 프로세스나 CPU 스로틀링 노이즈를 배제하기 위해 측정 전 1회 워밍업(Warm-up)을 수행하며, 재현성을 철저히 검증하려면 REPEAT 횟수(기본 10회)를 50~100회로 확대하여 표준편차와 최소/최대 편차를 확인하세요.
- **대형 N(1000×1000) 최악 비용 예시**: N=1,000일 때 $M = 1,000,000$ 셀로 단일 행렬당 메모리 약 8MB(float 64비트 기준)가 필요하며, CPU 순차 연산 시 1회 MAC에 약 25~30ms, 128개 필터 적용 시 1프레임당 약 3.5초가 소요되어 실시간 처리가 불가능해집니다.
- NPU 는 이 곱셈·덧셈을 수천 개 동시에 처리해서 $O(N^2)$ 의 일을 병렬로 나눕니다.
- **코드 수준 최적화 기법 요약**: 1) 캐시 미스를 최소화하는 타일링/블록화(Tiling/Blocking), 2) SIMD 벡터 연산(AVX2/NEON)을 통한 데이터 병렬화, 3) 1차원 평탄화(Flatten) 기반의 연속 메모리 공간 배치, 4) 멀티스레딩(OpenMP/ThreadPool) 병렬 분할 연산.

### 5. 보너스: 1차원 배열 최적화 비교 (모드 3, 동일 입력 · 10회)

| 크기 | 2D(ms) | 1D(ms) | 1D/2D |
|---|---|---|---|
| 3×3 | 0.0006 | 0.0004 | 0.74 |
| 5×5 | 0.0011 | 0.0008 | 0.73 |
| 13×13 | 0.0050 | 0.0042 | 0.85 |
| 25×25 | 0.0165 | 0.0161 | 0.97 |
| 101×101 | 0.2509 | 0.2713 | 1.08 |

- 작은 크기에서는 1차원 버전이 15~25% 빠릅니다. 바깥 반복문과 행(row) 꺼내기가 없어 고정 비용이 줄기 때문입니다.
- 큰 크기에서는 차이가 사라지거나 오히려 조금 느립니다. 2D 버전은 이미 바깥 반복에서 행을 한 번 꺼내 두고(`p_row = p_rows[i]`) 안쪽은 1D 와 똑같이 인덱스로 읽기 때문에, 칸당 비용이 거의 같습니다. Python 리스트는 C 배열처럼 메모리에 값이 붙어 있지 않아 캐시 이점도 크지 않습니다.
- 결론: Python 에서 1차원 변환의 효과는 **고정 비용 절감**이 주이고, 복잡도는 둘 다 $O(N^2)$ ($O(M)$) 로 같습니다. C 나 실제 NPU 처럼 메모리 접근이 연속인지가 중요한 환경에서는 1차원(연속) 배치의 효과가 훨씬 큽니다.
